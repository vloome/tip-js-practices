## 3. Реализация

### 3.1. HTTP-клиент

В `src/api-client.js` реализован общий клиент для методов `GET`, `POST`, `PATCH` и `DELETE`. Запросы получают заголовок `Accept: application/json`. Для запросов с телом объект преобразуется через `JSON.stringify`, а заголовок `Content-Type: application/json` добавляется только при наличии тела.

Клиент отклоняет `GET` с телом, проверяет HTTP-статус до проверки типа содержимого, возвращает `null` для `204 No Content` и разбирает JSON у остальных успешных ответов. Ошибки разделяются на `http`, `network`, `invalid-response`, `timeout` и `aborted`. Для тайм-аута применяется `AbortController`, также поддерживается внешний `AbortSignal`.

### 3.2. Доменый API

В `src/task-api.js` сосредоточены операции над задачами и категориями: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask` и `resetDemoData`.

Модуль проверяет фильтры, идентификаторы, структуру задач и категорий, уникальность ID и поле `meta.total`. Начальная загрузка задач и категорий выполняется параллельно через `Promise.all`. Для удаления ожидается пустой ответ `204`.

### 3.3. Состояние интерфейса

`src/form-validation.js` нормализует название и проверяет его длину, допустимый приоритет и существование выбранной категории. При ошибках функция возвращает ошибки полей и не отправляет запрос самостоятельно.

`src/task-view.js` создаёт карточки задач, отображает статус, приоритет и категорию. Список перерисовывается через `replaceChildren`. Названия задач и другие серверные данные выводятся через `textContent`, поэтому они отображаются как текст, а не как HTML.

### 3.4. Изменение данных

`src/app-controller.js` связывает предметный API и DOM-представление. Используются состояния `loading`, `ready`, `empty` и `error`. После успешного создания, редактирования, изменения статуса или удаления список повторно загружается с действующими фильтрами, поэтому источник актуальных данных — сервер.

При смене фильтра предыдущая загрузка отменяется с помощью `AbortController`. Дополнительно используется последовательный номер запроса: результат применяется только тогда, когда он относится к последнему запросу. Ошибка отменённой загрузки не показывается пользователю.

### 3.5. Защита от устаревшего ответа

В `src/variant.js` установлен вариант 4 с начальным фильтром `priority=medium`. Индивидуальный сценарий — создать задачу со средним приоритетом и проверить, что после повторной загрузки она появляется в текущей выборке.

## 6. Ответы на контрольные вопросы

**1. Почему `fetch` не отклоняет Promise при ответе 404?**

`fetch` не отклоняет Promise при HTTP-ошибках, поскольку сервер успешно вернул HTTP-ответ. Поэтому необходимо самостоятельно проверять `response.ok` и обрабатывать неуспешные статусы, например `404` и `500`.

**2. Почему ответ 204 нельзя разбирать вызовом `response.json()`?**

Статус `204 No Content` означает, что тело ответа отсутствует. Вызов `response.json()` попытается разобрать пустое содержимое и завершится ошибкой. Поэтому для такого ответа клиент возвращает `null`, не выполняя разбор JSON.

**3. Чем состояние `empty` отличается от `error`?**

Состояние `empty` означает, что запрос завершился успешно, но подходящих задач нет. Состояние `error` означает, что запрос не удалось выполнить или обработать. При `empty` пользователь может изменить фильтры, а при `error` — повторить запрос.

**4. Зачем отменять предыдущий запрос при смене фильтров?**

Предыдущий запрос может завершиться позже нового и перезаписать актуальный список устаревшими данными. `AbortController` позволяет отменять ненужные запросы, а проверка номера запроса дополнительно защищает интерфейс от применения устаревших результатов.

**5. Почему после мутации список повторно запрашивается у API?**

После создания, редактирования или удаления задачи повторный GET-запрос позволяет получить актуальное состояние данных с сервера с учётом выбранных фильтров. Благодаря этому интерфейс отображает подтверждённые сервером данные, а не только локально изменённый список.

## 7. Вывод

В ходе практической работы браузерное приложение связывается с учебным HTTP API. Общий HTTP-клиент отвечает за методы, заголовки, JSON и классификацию ошибок; предметный модуль — за операции с задачами и категориями; контроллер управляет состоянием интерфейса и повторной загрузкой данных.
