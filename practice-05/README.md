## Цель работы

Цель работы — научиться выполнять асинхронные HTTP-запросы, использовать `Promise` и `async`/`await`, проверять ответ сервера и отличать HTTP-ошибки от сетевых ошибок, ошибок формата ответа, тайм-аута и отмены запроса.

## 1. Эксперимент с очередями выполнения

До запуска прогнозируется, что синхронные сообщения `A`, `B`, `C` выводятся первыми. После завершения синхронного кода выполняются микрозадачи `D` и `E`, а затем задача таймера `F`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A → B → C → D → E → F` | Сначала синхронный код, затем микрозадачи Promise/`await`, затем таймер |
| Фактический результат | Вставить вывод `npm.cmd run example:order` | Сверить с прогнозом |

В дополнительном файле `examples/event-loop-extension.js` добавлен обработчик Promise с меткой `G`. Прогноз: `A → B → C → D → E → G → F`.

Фактический результат дополнительного эксперимента:

npm notice run tip-js-practice-05@1.0.0 example:order:extension
npm notice run node examples/event-loop-extension.js
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: дополнительная микрозадача Promise
F: задача таймера

Нулевой таймер не исполняется немедленно: он ставит callback в очередь задач, а текущий синхронный код и доступные микрозадачи должны завершиться раньше.

## 3. Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Предоставленный преподавателем учебный HTTP API; для обязательной части не изменяется |
| `src/api-client.js` | Сборка URL, GET-запрос, проверка статуса и типа содержимого, разбор JSON, тайм-аут, отмена и `ApiError` |
| `src/task-api.js` | Запрос задач и категорий, нормализация фильтров и проверка схемы данных |
| `src/variant.js` | Номер индивидуального варианта и значения его фильтров |
| `src/main.js` | Контрольный сценарий: загрузка данных, вывод таблицы и демонстрация ошибки 404 |
| `checks/student.checks.js` | Три дополнительные самостоятельные проверки |

`fetchFn` передаётся в `createApiClient`, чтобы подменить сетевой запрос тестовой функцией и проверять ошибки без реальной сети. HTTP-ошибка обрабатывается отдельно от сетевой: статус `404` или `503` означает, что HTTP-ответ получен. После разбора JSON дополнительно проверяется структура данных, так как корректный JSON не обязательно соответствует контракту API.

## 4. Реализация общего HTTP-клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | Удаляются завершающие `/`; допускаются только абсолютные URL `http` и `https` без query/hash | Модульные проверки конфигурации |
| Кодирование query-параметров | Используется `URL` и `URLSearchParams` | Проверка кириллицы, `&`, `false` и `0` |
| Заголовок `Accept` | `application/json` | Проверка параметров `fetchFn` |
| Проверка `response.ok` | HTTP-ответ с неуспешным статусом преобразуется в `ApiError` с `kind: "http"` | Проверки 404, 400 и 503 |
| Проверка `Content-Type` | Успешный ответ должен содержать JSON | `/debug/text` |
| Разбор JSON | Ошибка синтаксиса сохраняется как `cause` ошибки `invalid-response` | `/debug/invalid-json` |
| Ограничение времени | `AbortController` и таймер запроса | `/debug/delay` с коротким `timeoutMs` |
| Внешняя отмена | Внешний `AbortSignal` передаётся внутреннему контроллеру | Проверка `AbortController.abort()` |
| Ответ `204` | Возвращается `null`, тело не разбирается | Модульная проверка ответа 204 |

## 5. Классификация ошибок

| Сценарий | Ожидаемый `kind` | Фактические поля `ApiError` и результат |
|---|---|---|
| Задача `999` | `http` | Вписать `status`, `code`, `details`, `url` |
| `completed=yes` | `http` | Вписать `status` и `code` |
| `/debug/error` | `http` | Вписать `status` и `code` |
| `/debug/invalid-json` | `invalid-response` | Заполнить после запуска |
| `/debug/text` | `invalid-response` | Заполнить после запуска |
| API не запущен | `network` | Заполнить сообщение и `url` |
| Задержка больше тайм-аута | `timeout` | Заполнить сообщение и `url` |
| Отмена через `AbortController.abort()` | `aborted` | Заполнить сообщение и `url` |

Клиент использует единое поле `kind`: `http`, `network`, `invalid-response`, `timeout` или `aborted`. Для HTTP-ошибок дополнительно сохраняются статус и поля `error` от сервера, если они доступны.

## 7. Последовательная и параллельная загрузка

Выполнить команду при запущенном API:

| Запуск | Последовательные запросы, мс | `Promise.all`, мс |
|---:|---:|---:|
| 1 | 360.3 | 158.5 |
| 2 | 310.3 | 159.6 |
| 3 | 312 | 167 |

Два последовательных запроса ожидаемо занимают примерно сумму двух задержек, а параллельные — время, близкое к одной задержке. Измерения зависят от среды, поэтому в отчёт вносятся значения собственного запуска, а не числа из примера.

`loadInitialData` вызывает запросы задач и категорий до ожидания общего результата и собирает их через `Promise.all`. Если один Promise отклоняется, общий Promise также отклоняется; `Promise.all` сам по себе не отменяет второй запрос.

## 11. Отладка

В VS Code или отладчике Node.js поставить точки останова:

1. перед вызовом `fetchFn` в `src/api-client.js`;
2. после получения `response`;
3. перед `response.json()`;
4. в обработчике ошибки.

Для успешного и ошибочного запроса записать URL, `response.status`, `response.ok`, `Content-Type`, разобранный payload и итоговый `ApiError`. Добавить скриншот отладчика и кратко объяснить, какие значения были проверены.

## Вывод

В ходе работы реализуется разделение общего HTTP-клиента и предметного модуля задач. Общий клиент формирует URL, выполняет GET-запросы, проверяет статус и формат ответа, а также нормализует сетевые ошибки, тайм-ауты и отмену. Предметный модуль проверяет фильтры и структуру задач и категорий. Независимые запросы задач и категорий выполняются параллельно с помощью `Promise.all`. После выполнения всех проверок этот вывод следует дополнить фактическими результатами запуска.
