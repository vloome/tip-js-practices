## 1. Эксперимент с очередями выполнения

До запуска был составлен прогноз: синхронные сообщения `A`, `B`, `C` выводятся первыми. После завершения синхронного кода выполняются микрозадачи `D` и `E`, а затем задача таймера `F`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A → B → C → D → E → F` | Сначала синхронный код, затем микрозадачи Promise/`await`, затем таймер |
| Фактический результат `example:order` | `A → B → C → D → E → F` | Совпадает с прогнозом |

Фактический вывод `npm.cmd run example:order`:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

В дополнительном файле `examples/event-loop-extension.js` добавлен обработчик Promise с меткой `G`. Прогноз: `A → B → C → D → E → G → F`.

Фактический вывод дополнительного эксперимента:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: дополнительная микрозадача Promise
F: задача таймера
```

Результат соответствует прогнозу. Нулевой таймер не исполняется немедленно: он ставит callback в очередь задач, а текущий синхронный код и доступные микрозадачи должны завершиться раньше.

## 2. Наблюдение за HTTP-ответом

Эксперимент выполнялся при запущенном локальном API командой `npm.cmd run example:fetch`.

Фактический вывод:

```text
status: 200
ok: true
content-type: application/json; charset=utf-8
ids: [ 4, 13, 34 ]
meta: {
  total: 3,
  filters: { completed: false, priority: 'high', categoryId: null, q: '' }
}
```

| Свойство | Фактическое значение |
|---|---|
| URL запроса | `http://127.0.0.1:5505/api/tasks?completed=false&priority=high` |
| Метод | `GET` |
| Статус | `200` |
| `response.ok` | `true` |
| `Content-Type` | `application/json; charset=utf-8` |
| ID полученных задач | `[4, 13, 34]` |
| `meta.total` | `3` |
| `meta.filters.completed` | `false` |
| `meta.filters.priority` | `"high"` |
| `meta.filters.categoryId` | `null` |
| `meta.filters.q` | `""` |

Таким образом, сервер вернул успешный HTTP-ответ в формате JSON. В выборку вошли три невыполненные задачи с высоким приоритетом. Первоначально запрос завершился сообщением `fetch failed`, когда API был недоступен. После запуска сервера повторный запрос выполнился успешно.

Дополнительные адреса для ручного наблюдения: `/api/health`, `/api/tasks`, `/api/tasks/25`, `/api/tasks/999`, `/api/categories`. Для задачи `999` ожидается HTTP `404`; это HTTP-ответ сервера, а не отсутствие сетевого соединения.

## 3. Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Предоставленный преподавателем учебный HTTP API; для обязательной части не изменяется |
| `src/api-client.js` | Сборка URL, GET-запрос, проверка статуса и типа содержимого, разбор JSON, тайм-аут, отмена и `ApiError` |
| `src/task-api.js` | Запрос задач и категорий, нормализация фильтров и проверка схемы данных |
| `src/variant.js` | Номер индивидуального варианта и значения его фильтров |
| `src/main.js` | Контрольный сценарий: загрузка данных, вывод таблицы и демонстрация ошибки 404 |
| `checks/student.checks.js` | Три дополнительные самостоятельные проверки |

`fetchFn` передаётся в `createApiClient`, чтобы подменить сетевой запрос тестовой функцией и проверять ошибки без реальной сети. HTTP-ошибка обрабатывается отдельно от сетевой: статус `404` или `503` означает, что HTTP-ответ получен. После разбора JSON дополнительно проверяется структура данных, так как корректный JSON не обязательно соответствует контракту API.

## 4. Реализация общего HTTP-клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | Удаляются завершающие `/`; допускаются только абсолютные URL `http` и `https` без query/hash | Модульные проверки конфигурации |
| Кодирование query-параметров | Используются `URL` и `URLSearchParams` | Проверка кириллицы, `&`, `false` и `0` |
| Заголовок `Accept` | `application/json` | Проверка параметров `fetchFn` |
| Проверка `response.ok` | HTTP-ответ с неуспешным статусом преобразуется в `ApiError` с `kind: "http"` | Проверки 404, 400 и 503 |
| Проверка `Content-Type` | Успешный ответ должен содержать JSON | `/debug/text` |
| Разбор JSON | Ошибка синтаксиса сохраняется как `cause` ошибки `invalid-response` | `/debug/invalid-json` |
| Ограничение времени | `AbortController` и таймер запроса | `/debug/delay` с коротким `timeoutMs` |
| Внешняя отмена | Внешний `AbortSignal` передаётся внутреннему контроллеру | Проверка `AbortController.abort()` |
| Ответ `204` | Возвращается `null`, тело не разбирается | Модульная проверка ответа 204 |

## 5. Классификация ошибок

| Сценарий | Фактическая классификация | Статус и дополнительные сведения |
|---|---|---|
| Запрос задачи `999` | `kind: "http"` | HTTP `404`, код API `TASK_NOT_FOUND`, `details: { id: 999 }` |
| `completed=yes` | `kind: "http"` | HTTP `400`, код API `INVALID_QUERY` |
| `/api/debug/error` | `kind: "http"` | HTTP `503`, код API `SERVICE_UNAVAILABLE` |
| `/api/debug/invalid-json` | `kind: "invalid-response"` | Сервер отвечает статусом `200`, но тело содержит некорректный JSON |
| `/api/debug/text` | `kind: "invalid-response"` | Сервер отвечает статусом `200`, но тип содержимого — `text/plain`, а не JSON |
| API не запущен | `kind: "network"` | HTTP-статус отсутствует; первоначальный пример `fetch` завершился сообщением `fetch failed` |
| Задержка больше тайм-аута | `kind: "timeout"` | Запрос прерывается по ограничению времени; HTTP-статус отсутствует |
| Отмена через `AbortController.abort()` | `kind: "aborted"` | Запрос отменяется внешним сигналом; HTTP-статус отсутствует |

Клиент использует единое поле `kind`: `http`, `network`, `invalid-response`, `timeout` или `aborted`. Для HTTP-ошибок дополнительно сохраняются статус и поля ошибки API, если они доступны. Проверки клиента и интеграционные проверки подтверждают, что эти типы ошибок различаются.

## 7. Последовательная и параллельная загрузка

Для эксперимента выполнена команда `npm.cmd run example:parallel`. Скрипт трижды измеряет два последовательных запроса `/debug/delay` с задержкой 150 мс каждый, а затем два таких запроса через `Promise.all`.

Фактические результаты:

| Запуск | Последовательные запросы, мс | `Promise.all`, мс |
|---:|---:|---:|
| 1 | 360,3 | 158,5 |
| 2 | 310,3 | 159,6 |
| 3 | 312,0 | 167,0 |
| **Среднее** | **327,5** | **161,7** |

Среднее время последовательного выполнения составило около 327,5 мс, а параллельного — около 161,7 мс. В данном эксперименте `Promise.all` оказался примерно в 2,03 раза быстрее: экономия составила около 165,8 мс, или 50,6%.

Результат объясняется тем, что последовательный способ ожидает завершения первого запроса перед запуском второго. При `Promise.all` оба независимых запроса отправляются практически одновременно, поэтому ожидание задержек перекрывается. Время может немного отличаться при повторных запусках из-за накладных расходов и особенностей среды выполнения.

`loadInitialData` запускает запросы задач и категорий до ожидания общего результата и собирает их с помощью `Promise.all`. Если один Promise отклоняется, общий Promise тоже отклоняется; `Promise.all` сам по себе не отменяет второй запрос.
